# 账号池设计

## 核心思路

一个渠道（如 OpenAI）配多个账号（多个 API Key），AGW 自动管理这些账号的**选择、复用、故障处置**。

## 三层选择逻辑

```
① 优先级排队 → ② 粘性绑定 → ③ 健康检查
```

### ① 优先级排队

每个账号有一个 `priority` 值（越大越优先）。请求到来时按优先级从高到低尝试。

### ② 粘性绑定

同一消费者+模型在 TTL 内**尽量复用同一账号**。为什么？
- 上游 AI 有语义缓存，相同 prompt 命中缓存更便宜
- 减少账号切换，降低触发出错概率

TTL 默认可配（`affinity_ttl`），过期后自动重新选择。

### ③ 健康检查

选到账号后验证状态：
- `active`：可用
- `disabled`：已被标记故障，跳过
- `cooling`：在冷却期，暂不探测

## 故障降级

账号使用中遇到错误时，根据错误类型分类处理：

| 错误类型 | 行为 |
|---------|------|
| 401/403（认证失败） | 立即禁用 |
| 429（限流） | 禁用 + 设冷却时间 |
| 关键词匹配（封号/欠费） | 立即禁用 |
| 连续失败达到阈值 | 禁用 + 进入冷却 |
| 临时错误（502/503） | 计失败次数，切换账号 |

## 探测恢复

被禁用的账号不是永远不可用。AGW 有自动恢复机制：

```
disabled → 等待冷却期(一级/二级) → 按需探测 
  → 探测成功 → 恢复为 active
  → 探测失败 → 延长冷却或标记为彻底不可用
```

## 状态流转

```
active ←── 恢复成功 ←── probing
  │                      ↑
  │ 故障/限流             │ 冷却结束
  ↓                      │
disabled ──→ cooling ────┘
  │                      ↑
  └── 连续冷却周期 ──→ L2 cooling (更长冷却)
```

## 冷却引擎

- **一级冷却**（`probe_cooldown_duration`，默认 7200s）：首次故障
- **二级冷却**（`probe_cooldown_duration_l2`，默认 86400s）：反复故障
- 连续冷却周期递增，稳定后重置计数
